### 1. `blocker` — Task 3.7's verification command names a script that does not exist

**Finding.** Task 3.7 ("Store copies and full sweep") is verified by `node cdd/scripts/write-door-scripts.mjs && cmp of the 5 door copies identical && npm test exiting 0`. No such file exists anywhere in the repository, so the verify clause as written cannot be executed by a runner, and the task that carries Done-When line 4 (the `cdd/scripts/*.mjs` byte-identity criterion) has no runnable mechanical proof. `cdd/scripts/` holds only the five door copies (`adr-index.mjs`, `arch-extract.mjs`, `grammar-law.mjs`, `spec-drift.mjs`, `spec-extract.mjs`); door regeneration is `writeDoorScripts` invoked from `initStore`, not a standalone door script.

**Evidence.**

- `cdd/scripts/` — five files only; `cdd/scripts/write-door-scripts.mjs` absent (`ls` reports "No such file or directory"). A repository-wide grep for `write-door-scripts` hits only `cdd/changes/claim-map/tasks.md:75`.

- Precedent for the runnable form: `cdd/archive/20261020-deepen-fence-law/tasks.md:26,35` verifies the same surface by "cdd init re-copies cdd/scripts/*".

**Why it matters.** The Done-When criterion itself (`cdd/changes/claim-map/proposal.md:103`) is sound; only the task's verify clause is unreachable. A runner following 3.7 literally stops at a missing module, and the traceability row `cdd/changes/claim-map/tasks.md:86` then rests on a command nobody can run. This is the one place in the package where the verify-by clause is not mechanically reachable, and it sits on a fence-relevant surface (door-copy drift).

**Disposition.** `fixed:` — tasks.md 3.7's verify clause now names the real regeneration path: `node -e 'import("./lib/templates.mjs").then(m => m.writeDoorScripts(process.cwd(), process.cwd()))'` (writeDoorScripts is exported at lib/templates.mjs:257); the author ran the command on disk — exit 0, `git status --porcelain cdd/scripts/` empty (byte-identical rewrite), so the clause is mechanically reachable.

**Finding.** The delta asserts that the adrs op's governing answers "come from the shared claim map built in the claims-index module" and that the op "holds no glob translation" (`cdd/changes/claim-map/specs/adr/spec.md:5`). Today the op's single-path branch answers by matching each accepted ADR's globs against the **query string** — not against tracked files — with `governs` doing `adr.globs.some((g) => globToRe(g).test(file))` (`lib/adr-ops.mjs:50`, used at `lib/adr-ops.mjs:126`), and it answers `no ADR governs ${p}` when nothing matches (`lib/adr-ops.mjs:130`). Only the directory branch filters through the tracked file list (`lib/adr-ops.mjs:116-124`). If the builder produces claim sets over the tracked file list (Done-When 1 speaks of a per-file claiming loop over files; the directory branch is the model), then an untracked or non-existent path that a glob matches changes answer from a governing set to "no ADR governs …". The package never says which behaviour is authoritative for the single-path branch, and it never names a probe set for the before/after comparison, so a runner can satisfy both proofs on the AG3-style inputs and still ship a changed answer on a path that is glob-matched but untracked.

**Evidence.**
- `lib/adr-ops.mjs:50` `const governs = (adr, file) => adr.globs.some((g) => globToRe(g).test(file));`
- `lib/adr-ops.mjs:116` directory detection; `lib/adr-ops.mjs:117-124` directory branch iterating `trackedFiles(root)`; `lib/adr-ops.mjs:126` `governing = accepted(adrs).filter((a) => governs(a, p));` — no tracked-file gate; `lib/adr-ops.mjs:130` `no ADR governs ${p}`.
- `cdd/changes/claim-map/specs/adr/spec.md:5` — "The governing answers and the open-delta claims come from the shared claim map … the op holds no glob translation".
- `cdd/specs/adr/spec.md:42` (restated verbatim in the delta) — "answers a code path with every accepted ADR whose globs claim it".
- `cdd/changes/claim-map/tasks.md:74` (3.6b) and `cdd/changes/claim-map/proposal.md:102` (DW3) — "its `--code` answers … before and after over the live store, cmp" with no enumerated probe paths.
- `tests/acceptance/adr-ops.test.js:118` probes a tracked path (`lib/templates.mjs`), `:124` a directory, and `:136` a non-existent path (`no/such/file.mjs`) whose expected answer is the empty-answer text at `lib/adr-ops.mjs:130` — precisely the case where a tracked-file claim map and a query-string glob match disagree; the package states neither which answer survives nor that the existing expectation is the one to keep. AG3's real-door probe (`tests/acceptance/adr-index-agreement.test.js:111-165`) uses a tracked file (`src/thing.mjs`) only.

**Why it matters.** This is the byte-identity contract's coverage hinge: the proof is only as strong as the inputs it compares. Without a named probe set (at minimum: one tracked glob-claimed path, one untracked glob-matching path, one directory, one unknown path), "byte-identical" does not constrain the surface the What Changes names most prominently.

**Disposition.** `fixed:` — authoritative semantics decided and pinned: the single-path branch's answer (query-string glob match, untracked and non-existent paths included) is the behavior byte-identity keeps; the map reproduces it via a per-path governing query that tests the path against the retained compiled globs — a query API in the map module, not a claiming loop over files. Delta description rewritten to say exactly that (single-path answers via the map's per-path governing query; directory answers and open-delta claims from the map's file sets); DW3 and 3.6(b) now name the probe set — tracked claimed path `lib/templates.mjs`, an untracked path matching a governing glob, and non-matching `no/such/file.mjs`; and the new gherkin scenario "The op answers from the shared claim map" pins op == map per-path query for a tracked and an untracked path.
