# spec-model

## Why

Spec-file parsing is restated in five places: the guard re-parses every spec four times over (pins/globs, memory claims, corrections, G-check fences), the extractor carries its own private pin scan and its own pre-PF-20 glob matcher, and the store keeps a third block grammar in parseDelta/parseLivingSpec. The restatements have already diverged — the extractor counts a `# Verified by:` lookalike outside a gherkin fence as a pin (the guard does not), and its stale matcher makes every single-star glob claim zero files, so the brownfield burn-down map quietly under-reports owned territory. Every future parse fix must land in five places or drift again.

## What Changes

- `scripts/grammar-law.mjs` (the law module every door already shares) gains `parseSpecModel(text)`: one function that parses a spec file once into its parts — requirement blocks, delta operation blocks, fence-masked pins, `Code:` globs compiled with the shared matcher, and the extracted fences. The module's one new import edge is `globToRe` from `scripts/adr-index.mjs` (both travel in the copied door set).
- `scripts/spec-drift.mjs` reads the model at all four re-parse sites (pinsOf/codeGlobs, memoryClaimsOf, correctionsByCap, the G-check); pin resolution and verdict logic stay put, check order and report format are untouched, and the guard's full-corpus stdout/stderr/exit are pinned byte-identical before/after on a clean tree at bc4b867 (PF-27's worktree recipe).
- `scripts/spec-extract.mjs` reads the same model; its private pin scan and private globToRe are deleted. Two deliberate behavior changes: a `# Verified by:` lookalike outside a gherkin fence (quoted in a doc fence or prose) pins nothing, and a star glob claims the files it names — the extractor now agrees with the guard by construction.
- `lib/store.mjs` parseDelta/parseLivingSpec become thin adapters over the model, keeping their exact exported shapes (`{op, requirement, block, startLine, text}`); validate and archiveChange are untouched consumers.
- Store copies `cdd/scripts/*.mjs` are regenerated byte-identical; DOOR_SCRIPTS membership stays exactly the five current entries.

## Solutions Considered

- gherkin (the parse): the law module `scripts/grammar-law.mjs` already owns every shared grammar surface (PIN_COMMENT, CODE_LINE, extractFences, maskFences) — adopted as the model's home; a new door-script file was rejected (grows every adopting copy set for zero new law; the mission pins DOOR_SCRIPTS at five) as was housing it in the guard (heaviest, door-coupled consumer; text-only parse belongs with the grammar law). Full alternatives in design.md.
- glob compilation: the claims-index matcher `globToRe` in `scripts/adr-index.mjs` (ADR-0007's mechanism, PF-20's fixed semantics, pinned by "Code globs compile to precise file claims") — adopted by import; moving the translation into the law module was rejected (AG2 pins it defined exactly once in adr-index.mjs), as was leaving compilation to consumers (the exact divergence this change kills).
- store block grammar: the existing parseDelta/parseLivingSpec exported shapes — adopted unchanged as thin adapters over the model; a re-export module was rejected (new file for a shape two consumers already agree on).
- guard structure: the existing per-law structure — kept as-is; restructuring into pure checks over the model is run 2's scope, rejected here because it would invalidate the byte-identity proof's meaning.

## Non-Goals

- No restructure of spec-drift.mjs into pure-check functions or a git adapter (future run 2).
- No change to lib/adr-ops.mjs's claim-map derivation (future run 3), no ops registry or index.ts dispatch work (future run 4).
- No store-format changes of any kind; LAW_VERSION stays 2 (no grammar change — one dialect moves home, none is born).
- No new ADR: extending grammar-law's mandate is ADR-0007's existing mechanism, not an amendment.

## Capabilities

- gherkin: ADDED "The spec model is the single parse" (specs/gherkin/spec.md) — the spec-parsing law precedent ("The ADR claims index is single-sourced" lives in this capability); every file the delta's Code line names is already gherkin-owned surface, so no cross-capability ownership moves.

## Decisions followed

ADR-0007 (one grammar module behind every door — the model is that module's next chapter), ADR-0006 (pins are fence comments — the extractor now honors the same fence masking), ADR-0001 (zero-dependency Node tooling at the doors — no new dependency, node builtins + the existing door pair only), ADR-0003 (the store is plain markdown — parse adapters change no store byte), ADR-0012 (comments are shape-of-code documentation only), ADR-0011 (ticks are claims and pins hit real doors — new scenarios pin the real extractor and guard), ADR-0008/ADR-0010 (advisory reviews, cold reviewers — this change's review points run that grammar).
