# green-start-warning

## Why

The loop assumes every change starts from a green door 3, and today it doesn't, in two ways:

1. `cdd new` says nothing when the store is already red at start (unresolvable pins, orphan acceptance tests, stale coverage). The next runner inherits a red it did not cause and burns a session discovering that. This happened: commit d967404 landed `smoke.mjs` spec-less; the next change started red through no fault of its own.
2. The scaffold itself manufactures red: the delta template pins a placeholder acceptance-test path (`tests/acceptance/${capability}-<scenario>.test.js` — the capability is interpolated, only `<scenario>` is a template token), so guard L1 ("every pin resolves") is red from scaffold until the real test lands — the guard cries wolf during exactly the window where red means nothing.

A change should start green and know it: `cdd new` surfaces the real door-3 verdict as a non-blocking warning, and the scaffold's placeholder pins no longer count as claims.

## What Changes

- `createChange` runs the real guard (`cdd/scripts/spec-drift.mjs`, full scan) before writing any artifact, capturing both stdout and stderr, and returns its verdict as `preexistingRed: string[]` on a successful scaffold — empty when the scan exits 0; otherwise one verbatim entry per issue line the guard printed on stderr (the indented, bracket-tagged lines, in order; the summary line and everything on stdout are not findings). If the guard exits non-zero with no issue lines it aborted rather than scanned (e.g. `@cucumber/gherkin` missing): exactly 1 entry states the guard could not complete, carrying the abort message; a missing script or spawn failure yields exactly 1 entry stating the guard could not run. Whatever the guard reports, we report; there is no second, partial implementation of the law. The guard runs synchronously (`execFileSync`); `createChange` stays a synchronous function — no call-site changes. The scaffold always proceeds.
- The `new` tool op and the `/cdd-new` command render a "pre-existing red at change start — this change did not cause it" block listing the findings, followed by a hint to fix the store or knowingly accept the red. Both surfaces stay silent when `preexistingRed` is empty. The warning never blocks scaffolding.
- The law learns placeholder pins: `isPlaceholderPin` (a pin containing the scaffold's placeholder marker — the angle-bracket form of `scenario` or `name`, the same token family the draft door already treats as unfilled) joins `scripts/law.mjs`, `LAW_VERSION` goes 1 → 2, and this repository's store copies `cdd/scripts/law.mjs` and `cdd/scripts/spec-drift.mjs` are regenerated byte-identical; adopting stores pick both up when `cdd init` refreshes `cdd/scripts/*` (living law). Any other angle-bracket shape is not a placeholder and stays red even in open deltas.
- Guard L1 skips placeholder pins found in open-delta specs (`cdd/changes/*/specs/**`) only, and reports every skip as an informational stdout line ("N placeholder pin(s) skipped in open delta <name> — expected until implementation") — a skip is never silent. Living specs keep full L1 strictness: a placeholder pin there is still red.
- Draft and strict validation are untouched: the scaffold stays draft-red on placeholders until the real test exists (living law, pinned by the existing smoke suite), and strict validation still refuses unresolved pins at archive. The tolerance is scoped to the guard's view of the scaffold window; every other door is as strict as before.

## Solutions Considered

- In-process mirror of guard L1 inside `createChange` — rejected: it would have missed the actual incident (d967404 was L2 staleness, not L1) and forks the door-3 law into a second implementation the guard can drift from; the door-3 grammar is law-behind-every-door territory (ADR-0007), and the guard runs in seconds.
- Dropping the placeholder pin from the delta template — rejected: the pin is the contract being promised (a real acceptance test will pin this delta); removing it makes the scaffold lie in the other direction and weakens the acceptance-first discipline.
- Making the guard itself warn-but-pass on unresolved pins generally — rejected: unsponsored generalization; only the scaffold's self-declared placeholders are skipped, everything else stays red.

## Non-Goals

- No git-topology checks in `createChange` beyond what the guard itself reports (L2 staleness, orphans, ADR coverage arrive via the guard verdict, not re-implemented here).
- No change to `cdd validate` draft/strict semantics, `cdd/rules.md`, or the review-point wiring.
- No guard redesign: the skip is one scoped exception plus one report line, not a new verdict tier.
- No new ADR: this clarifies ADR-0006 (pin dialect tolerance during the scaffold window) and ADR-0007 (the predicate lives with the grammar); it adds no second implementation. The edited surfaces stay within their existing decisions: `scripts/**` under ADR-0001 (zero-dependency doors — the guard spawn adds no dependency), `index.ts` under ADR-0002, `lib/store.mjs` under ADR-0003.
