# 20261024-scaffold-honesty

## Why

The proposal scaffold embeds its own instructions as an HTML comment, but `validateProposal` counts Done-When lines and scans for placeholder phrases over the raw proposal text — so an author who fills every placeholder in place and keeps the instruction comment is falsely rejected: the scaffold's own `Done-When: 1-5 completion criteria` line phantom-counts as a sixth criterion (reproduced: "6 Done-When criteria (max 5 — split the change)") and its Non-Goals instruction phrase trips the placeholder check ("template placeholders still unfilled"). The honest fill is punished; only deleting the comment the scaffold asked the author to keep passes the door (PF-1). Separately, changing the scaffold legitimately requires editing the S-series smoke pins that pin its shape, and no law line says so (PF-2) — the coupling is word-of-mouth.

## What Changes

- `validateProposal` masks HTML comment blocks before the Done-When count and the placeholder check: the scaffold's own instruction text is never proposal content. Section-presence and `Code:` checks still run on raw text; an unclosed `<!--` stays unstripped (still flags).
- S32's round-trip fill keeps the proposal instruction comment (the honest fill; tasks/delta comment handling unchanged), and a new S39 smoke pin pins the comment-kept verdicts directly: 5 real Done-When lines + comment → no proposal error; full comment-kept fill → no placeholders error.
- Rule 7 of the law gains one sentence — a change that edits scaffold text legitimately edits, in the same change, the pins that pin the scaffold's shape (in this repository, the S-series checks in tests/smoke.mjs) — single-sourced in `RULES_MD`, byte-identical in `cdd/rules.md` (PF-2's doc line).
- Scaffold wording itself is unchanged (LDW4's pinned instruction text stays green).

## Solutions Considered

- gherkin: `maskCodeSpans` in lib/validate.mjs (adopted as the shape precedent for "text that is not content" — the comment mask reuses the same blanking approach at proposal scope; a new `maskHtmlComments` helper, not an overload of the existing mask's meaning).
- gherkin: strip the instruction comment from the scaffold entirely (rejected: the comment is the honest how-to and travels with the template into adopting stores; LDW4 pins its wording verbatim; PF-13's fix already joined the placeholder check to `validateProposal` with the comment kept).
- gherkin: emit instructions out-of-band, a separate file the validator never sees (rejected: `proposalTemplate` embeds `PROPOSAL_INSTRUCTION` by design — one artifact, single-source law; splitting breaks the byte-pinned mirror).
- gherkin: narrow the placeholder vocabulary instead of masking comments (rejected: the false trip is the instruction's own phrases, not over-broad patterns; narrowing would weaken the fresh-scaffold red that S4 and S32 leg 1 pin as exactly-3).
- gherkin: for PF-2's line, the cdd-code-review skill vs the law's rule 7 (adopted rule 7: binding on every future scaffold change whether or not it reaches R3; the skill is review procedure; the single-source seam already carries the mirror edit).

Governing decisions (cited per the guard's A1 gate):

- ADR-0006 (one Feature document per requirement; pins are `# Verified by:` comments inside the fence): both ADDED requirements carry their pins as fence comments; no heading scenarios.
- ADR-0007 (the law behind every door): the comment mask lives once in lib/validate.mjs — every verdict path (draft, strict, validateBoth) flows through the same `validateProposal`; no copied fragment.
- ADR-0008 (model-run reviews are advisory findings): R2's should-finding was disposed by the author, not enforced by a gate; the finding and disposition are recorded in reviews/r2-change-review.md.
- ADR-0009 (single-source the loop law): the rule-7 sentence is authored once in `RULES_MD` (lib/templates.mjs); cdd/rules.md is its regenerated byte-identical mirror (SSL3 pins the identity).
- ADR-0010 (reviewer independence is loop law): R2 ran as a cold sub-agent on a non-author family (opencode-zen/gpt-6-luna vs author zai), read from completion metadata.
- ADR-0011 (ticks are claims and pins hit real doors): every tick here cites a real command run — S39/S32-leg-2 and the 3.2 pin were observed RED before the mask and the sentence landed; the pin imports the real module (`lib/templates.mjs`) and reads the real store copy.
- ADR-0012 (comments are shape-only documentation): the mask honors the same boundary in artifacts that ADR-0012 draws in code — an embedded instruction comment is scaffold shape, not proposal content; `maskHtmlComments`' own doc comment stays shape-only.

## Non-Goals

- No validator behavior change beyond the scaffold↔placeholder interplay PF-1 names — no new gates, no thresholds, no split-considered law (PF-32 is its own change).
- No living-spec restructure or capability split (PF-6/PF-32 stay parked).
- No change to the tasks/delta validators — their instruction comments sit outside the checked regions (delta comment precedes `## ADDED Requirements`; the tasks `<task>`/`<pin>` check runs per implementation item), verified by reading `validateDelta`/`validateTasks`.
- No scaffold wording edits — the fix is validator-side honesty, not rewording the instruction.
